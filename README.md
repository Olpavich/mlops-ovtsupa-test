# Проект: Антифрод-система для онлайн-платежей

## 1. Цели системы
Система разрабатывается для достижения следующих целей:
- **Бизнес цель:** Снизить  ущерб от мошенничества до **500 000 рублей** и пропускать не более **2 мошеннических транзакций на 100** (соответствие конкурентам).
- **Техническая цель:** Обеспечить время ответа системы менее **1 секунды** и выдерживать пиковую нагрузку в **400 транзакций/сек**.
- **Качество сервиса:** Долю ошибочно отклоненных корректных транзакций (ложные срабатывания) должна быть **ниже 5%**, чтобы избежать ухода клиентов.
- **Сроки:** MVP через **3 месяца**, финальную версию сдать через **6 месяцев**.

## 2. Метрики машинного обучения
Для оценки модели будет использоваться **F1-Score**.
- Вместо стандартного Accuracy (просто точность), где модель может просто предсказывать «все чисто» и получить 99% Accuracy, будет использоваться F1-Score.
- **Суть F1:** Это баланс между **Precision** (чтобы не было много ложных блокировок >5%) и **Recall** (чтобы поймать как можно больше мошенников). Оптимизация F1 заставит модель искать «золотую середину» и соответствовать требованиям заказчика.

## 3. Анализ проекта с использованием MISSION Canvas

### 3.1 Money and Milestones

- **Бизнес-ценность:** Снижение финансовых потерь клиентов и компании от мошеннических транзакций.
- **Бюджет:** 10 млн рублей (без учета зарплат специалистов) на реализацию проекта.
- **Ключевые этапы:**
  - Месяц 3: MVP для демонстрации заказчику.
  - Месяц 6: Финальная версия системы, готовая к промышленной эксплуатации.

### 3.2 Ideas

- **Гипотеза:** Исторические данные о транзакциях содержат паттерны, которые помогут обучить модель отличать мошеннические операции от корректных.
- **Подход:** Мы обучим модель на этих данных. Она будет изучать примеры прошлых транзакций (каких много, а каких мало) и запоминать, какие комбинации признаков чаще всего встречаются у мошенников. В будущем, когда придет новая транзакция, модель быстро сравнит её с изученными примерами и выдаст вероятность мошенничества.

### 3.3 Strategy (Стратегия)

- **Основной план:**
  1. Сбор и предобработка исторических данных.
  2. Разработка и обучение модели классификации.
  3. Развертывание модели в облаке в виде микросервиса с REST API.
  4. Интеграция с существующей системой онлайн-платежей.
- **Запасной план (если модель не достигает целевых метрик):**
  - Внедрение гибридной схемы: модель маркирует подозрительные транзакции, а финальное решение принимает оператор службы безопасности.

### 3.4 Squad and Skills (Команда и компетенции)

- **Необходимые роли:**
  - Data Scientist: исследование данных, построение и обучение модели.
  - Data Engineer: настройка потоков данных и хранения.
  - MLOps Engineer: разработка пайплайнов CI/CD, контейнеризация и развертывание модели, обучение, мониторинг.
- **Дефицит компетенций:** Требуется привлечение эксперта по информационной безопасности для работы с конфиденциальными данными.

### 3.5 Inputs (Входные данные)

- **Источники:** CSV-файлы с полной историей транзакций за фиксированные периоды.
- **Ограничения:** Данные содержат персональную информацию клиентов, что требует строгого соблюдения политик безопасности и шифрования.
- **Объем:** Оценивается в десятки тысяч записей, достаточных для обучения модели.

### 3.6 Outputs (Результаты)

- **Основной результат:** Обученная модель, готовая к эксплуатации.
- **Сопутствующие артефакты:**
  - Техническая документация (архитектура, API-спецификация, инструкция по развертыванию).
  - CI/CD пайплайны для автоматического переобучения и деплоя.
  - Система мониторинга качества предсказаний.

### 3.7 Nuances (Нюансы и риски)

- **Главный риск:** Дрейф данных (concept drift) — изменение поведения мошенников делает модель устаревшей.
- **Меры предосторожности:**
  - Автоматическое переобучение модели на свежих данных (не реже 1 раза в неделю).
  - Ручной аудит отклоненных транзакций для сбора новой разметки.
  - Настройка алертов при падении метрик качества ниже пороговых значений.
- **Дополнительные риски:** Утечка данных, недоступность облачного провайдера, превышение бюджета на облачные ресурсы.

### 3.8 Communication (Коммуникация)

- **Внутренняя:** Ежедневные синхронизации команды, еженедельные ретроспективы.
- **С заказчиком:** Демонстрация промежуточных результатов раз в 2-3 недели для подтверждения соответствия требованиям.
- **Документирование:** Ведение CHANGELOG и обновление README по мере развития проекта.
